<objective>
Add the `ai-engine` service to `backend/docker-compose.yml` and wire the Go `api` service to it (FND-02).

Purpose: The Python engine built in Plan 01 must be runnable as part of the standard local stack (`docker compose up`), internal-only (no exposed host port), health-checked, and discoverable by the Go backend as `http://ai-engine:8000` with the shared `X-AI-Engine-Token`.

Output: A compose stack where `docker compose up -d ai-engine` produces a healthy `academio-ai-engine` container on the internal network, and `api` carries `AI_ENGINE_URL` + `AI_ENGINE_TOKEN` env so the FND-04 unconditional config validation passes when the api container runs.

**Architectural decisions (locked in research):**
- **NO `ports:` mapping** on ai-engine — the engine is internal infrastructure; only the Go backend (same compose network) may reach it. This is the multi-tenant security posture: never expose an unauthenticated-capable service to the host/outside world.
- **Healthcheck uses `python -c urllib`**, NOT `curl -f` — the `python:3.13-slim` image (Plan 01 Dockerfile) ships no curl (unlike qdrant/gotenberg images). It targets the **unauthenticated** `GET /health` liveness endpoint so the healthcheck needs no token.
- **NO `depends_on: api → ai-engine`** — the Go backend must start even if the engine is down (config validation is env-based, not connectivity-based; the circuit breaker in `internal/ai/circuit_breaker.go` handles engine downtime). Adding a hard dependency would make the whole stack fail on engine build errors.
- **`api` env additions** (`AI_ENGINE_URL`, `AI_ENGINE_TOKEN`) are REQUIRED because Plan 04 makes engine config validation unconditional — without them the api container would crash-loop on startup.
- **Shared `uploads_data` volume** — the document pipeline (extract) will need the same files the API writes to `/app/uploads` (compose line 92 pattern).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| compose network → ai-engine | The ONLY trusted caller is the Go `api` service on the same compose network; the engine's token-protected endpoints are never exposed to the host or the internet |
| host → ai-engine | MUST be closed — no ports mapping. If this boundary opened, an unauthenticated liveness endpoint and token-auth'd AI endpoints become reachable from anywhere on the host |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | S (Spoofing) | ai-engine auth | mitigate | `X-AI-Engine-Token` required on all `/v1/*` routes (Plan 01); compose injects `AI_ENGINE_TOKEN` with default `local-dev-token` — the same value Plan 04 writes to `.env`, so host-run and compose-run tokens agree. |
| T-03-02 | E (Elevation of Privilege) | host exposure | mitigate | NO `ports:` mapping on ai-engine (architectural decision, verified in Task 2 via `docker compose port` returning empty). The engine is internal infrastructure — same posture as the Go backend's qdrant/gotenberg internal links. |
| T-03-03 | I (Information Disclosure) | token in compose | accept | Token appears in compose via `${AI_ENGINE_TOKEN:-local-dev-token}` interpolation; dev-only default documented in .env.example; production must supply a real secret. Compose is a dev/ops artifact, not a secret store (same pattern as existing `JWT_SECRET` line 81). |
| T-03-04 | D (Denial of Service) | healthcheck | mitigate | urllib healthcheck has `timeout=3` and 5 retries with 10s interval + 10s start_period — a hung uvicorn boot is detected without starving the engine of CPU during slow starts. |
| T-03-05 | D (Denial of Service) | stack coupling | mitigate | No `depends_on: api → ai-engine`: backend boots and serves non-AI traffic while the engine is down; `internal/ai/circuit_breaker.go` handles runtime engine outages. Prevents engine build failure from taking down the whole stack. |
</threat_model>
